# Интеграция внешних E2E-тестов с GraphQL Coverage Proxy

Документ для разработчиков бэкенда, тестов и фронтенда карты покрытия.
Источники контракта: [app/contracts.py](../app/contracts.py),
[REST API для фронтенда](frontend-api.md), [app/api_models.py](../app/api_models.py)
и [app/services.py](../app/services.py).

Проверено 14 ноября 2026 года на `main`:
`b5b82ecb09fd7d62292c5c80d7aa533ff7092fb6`.
**Сейчас реализованы REST API, импорт SDL и внутренняя запись наблюдений.
Работающего сквозного сбора покрытия через `/graphql` в этом коммите нет.**
Ниже отдельно обозначены требования к интеграции, которую ещё нужно реализовать.
Примеры подключения E2E применимы после выполнения зависимостей из раздела 10.

## 1. Создание, выполнение и завершение test_run

`test_run` — запись прогона, привязанная к одному снимку GraphQL-схемы.
В REST API она называется run. JSON использует camelCase, идентификаторы —
строки UUID, время — ISO 8601 UTC. Один прогон может объединять весь внешний
E2E-набор; отдельная сущность тест-кейса и связь запроса с тест-кейсом отсутствуют.

| Этап | Действие | Результат |
| --- | --- | --- |
| Подготовка сервиса | `GET /api/services`; при необходимости `POST /api/services` с `{"key":"demo-api","name":"Demo GraphQL API"}` | Использовать `id` сервиса; повторный key даёт 409 |
| Подготовка схемы | `POST /api/schemas/import` с `{"serviceId":"<service UUID>","sdl":"<реальный SDL upstream>"}` | 201; `id` снимка использовать как `snapshotId`; повторный импорт той же схемы возвращает существующий снимок |
| Выбор снимка | `GET /api/schemas?serviceId={serviceId}` | Выбрать версию, соответствующую реальному upstream |
| Создание прогона | `POST /api/runs` с телом ниже | 201; сохранить `id` как runId; `status="running"`, `finishedAt=null` |
| Выполнение | Передать runId всем участникам набора; отправлять GraphQL через прокси с `X-Coverage-Run-Id` | После реализации связки прокси и анализатора появятся наблюдения и покрытие |
| Ожидание | Дождаться всех GraphQL-ответов и сохранения наблюдений; остановить фоновый polling приложения | Новые запросы больше не поступают |
| Завершение | `POST /api/runs/{runId}/finish`, без тела | 200; объект прогона со `status="completed"` и заполненным `finishedAt` |
| Отчёт | `GET /api/runs/{runId}/coverage` и `/requests` | Сохранить карту и журнал даже при падении E2E |

Тело создания прогона:

```json
{
  "snapshotId": "162ef82d-d806-4f08-b901-e08b5d9228e2",
  "name": "E2E Regression",
  "metadata": {
    "branch": "main"
  }
}
```

UUID здесь иллюстративный: нужен `id` реально импортированного снимка.
`metadata` — произвольный JSON-объект; в нём можно хранить идентификатор внешнего
запуска и commit SHA, но не секреты. Список прогонов:
`GET /api/runs?snapshotId={snapshotId}`.

На одном снимке допускается только один `running`-прогон, иначе создание даёт 409.
Параллельные workers одного набора должны использовать один заранее созданный
runId. Каждый worker не должен создавать и завершать собственный прогон на том
же снимке. Независимые запуски на одном снимке нужно сериализовать.

Оркестратор завершает прогон в `finally`/teardown и при неуспешных тестах.
`completed` означает окончание сбора, а не успешное прохождение тестов:
endpoint `/finish` всегда выставляет `completed`. Хотя модель БД допускает
`failed`, REST-операции установки этого статуса нет. Повторный `/finish` даёт 409,
неизвестный runId — 404, некорректный UUID в REST-пути — 422.
После завершения `record_observation()` отвергает новые записи.

Завершение и запись наблюдения блокируют одну строку прогона. Если `/finish`
опередит ещё не записанный запрос, тот не будет сохранён. Поэтому будущая
интеграция должна обеспечить сохранение до выдачи GraphQL-ответа клиенту либо
явный способ дождаться записи. Сейчас HTTP API ожидания/flush нет; фиксированная
задержка не является гарантией завершения записи.

## 2. Контракт X-Coverage-Run-Id

Для запроса, который должен попасть в покрытие, E2E-клиент передаёт:

```http
X-Coverage-Run-Id: 57b03e76-29a9-4d9c-a961-1d47ba4f850f
```

Требования к интеграции:

- Значение — один UUID из ответа `POST /api/runs`, без префикса `Bearer`.
  Имена HTTP-заголовков регистронезависимы.
- Заголовок добавляется к каждому учитываемому GraphQL HTTP-запросу. Он не нужен
  для `/api/...`, загрузки HTML, изображений и обращений к сторонним сервисам.
- runId связывает запрос с прогоном и его снимком схемы. Он не выбирает upstream,
  не заменяет авторизацию и не служит идентификатором отдельного тест-кейса.
- Только существующий `running`-прогон может принимать наблюдения.
  При отсутствующем, некорректном, неизвестном или завершённом runId нельзя
  приписывать запрос другому активному прогону или создавать прогон автоматически.
- Прокси читает служебный заголовок для атрибуции и удаляет его перед upstream.

**Статус реализации:** в `main` заголовок ещё никто не обрабатывает.
PR #3 удаляет его при пересылке, но не проверяет UUID/состояние прогона и не пишет
наблюдения. Политика HTTP-ответа прокси при отсутствующем/некорректном runId
пока не реализована и не определена REST-контрактом. Нельзя переносить коды ошибок
REST API на `/graphql` или считать такой запрос гарантированно записанным.

## 3. Куда направлять GraphQL-запросы

Целевая последовательность трафика:

```text
E2E → реальное веб-приложение → POST <coverage-proxy>/graphql
                                  → реальный GraphQL upstream
                                  ← оригинальный GraphQL-ответ
                           ← ответ для приложения
```

GraphQL URL тестируемого приложения должен быть настроен на адрес прокси
**до первого запроса**, включая запросы при открытии страницы и входе в систему.
Прокси, в свою очередь, направляется на реальный upstream. В PR #3 это настройка
окружения `TARGET_GRAPHQL_URL`; в текущем `main` её ещё нет. Адрес не задаётся
через runId или REST-запись сервиса: сервис содержит только key и name.

Прямые обращения приложения к upstream обходят наблюдение. Если запросы выполняет
сервер приложения (SSR/BFF), его GraphQL-клиент тоже должен использовать прокси
и передавать runId: маршрутизация браузера Playwright такие запросы не охватывает.
Фронтенд карты обращается к `/api/...`; он не создаёт наблюдения самостоятельно.

Для браузера нужны рабочие CORS и OPTIONS на фактическом адресе прокси.
При запросе с заголовком браузер должен иметь право передать `X-Coverage-Run-Id`
и используемые приложением заголовки, включая `Authorization`.
Текущий FastAPI разрешает все методы и заголовки для origin из `CORS_ORIGINS`
(по умолчанию `http://localhost:5173`), но `allow_credentials` не включён.
Cross-origin cookies требуют отдельного решения; для демо с cookie-auth удобен
один origin с заранее настроенной маршрутизацией. Этот документ её не меняет.

## 4. Authorization и прозрачная пересылка

Прокси обязан передать исходный `Authorization` приложения upstream без замены
его на runId или токен Coverage API. Если клиент не передал `Authorization`,
прокси не должен придумывать его. Аутентификация, cookies и права пользователя
остаются частью реального приложения.

PR #3 реализует пересылку исходных байтов тела и применимых заголовков, включая
`Authorization` и `Cookie`. Исключаются `X-Coverage-Run-Id`, hop-by-hop заголовки
и заголовки, перечисленные в `Connection`; `Host` и `Content-Length` формируются
заново. Это также означает, что некорректный клиентский `Connection: Authorization`
приведёт к исключению `Authorization` как hop-by-hop заголовка.

HTTP-статус и тело upstream, включая GraphQL `errors` и HTTP 4xx/5xx, должны дойти
до приложения. Нельзя заменять их ответом с рассчитанным покрытием. Анализатор
читает копию данных для анализа, а не изменяет GraphQL-запрос или ответ.
Не сохраняются текст операции, variables, `Authorization` и cookies;
в наблюдение может попасть только SHA-256 текста операции (`query_hash`).

## 5. Proxy → GraphQL Analyzer → record_observation()

Это внутренняя Python-интеграция, а не публичный REST endpoint для загрузки
«готового покрытия». Её ещё нет в `main` и PR #3.

1. Proxy получает runId и находит снимок, к которому относится прогон.
2. Для анализа JSON-тела формируется `GraphQLQueryInput`: `query`,
   `operation_name` (JSON `operationName`) и `variables` (по умолчанию `{}`).
   Исходное тело для upstream сохраняется без переписывания.
3. Analyzer разбирает выбранную операцию и проверяет её по схеме прогона.
   Результат — существующий `AnalysisResult`, а не список клиентских ID полей.
4. Proxy получает реальный ответ upstream и формирует правдивые HTTP/GraphQL
   признаки, в том числе наличие ключа `data` и GraphQL-ошибок.
5. Proxy вызывает `await record_observation(session, observation)` с
   `RequestObservationInput`. После commit сохранённое наблюдение доступно REST API.

Существующие структуры из `app/contracts.py`:

| Структура | Поля |
| --- | --- |
| `FieldReference` | `type_name: str`, `field_name: str` |
| `GraphQLQueryInput` | `query: str`, `operation_name: str \| None = None`, `variables: dict = {}` через default factory |
| `AnalysisResult` | `status: str`, `operation_type: str \| None`, `operation_name: str \| None`, `fields: tuple[FieldReference, ...] = ()`, `error_code: str \| None`; необязательные значения по умолчанию `None` |
| `RequestObservationInput` | `run_id: UUID`, `analysis: AnalysisResult`, `http_method: str`, `http_status: int \| None`, `response_has_data: bool \| None`, `graphql_has_errors: bool \| None`, `duration_ms: int \| None = None`, `query_hash: str \| None = None` |

Сервис принимает статусы анализа `success`, `parse_error`, `validation_error`,
`unsupported`, `internal_error`. Неуспешный анализ обязан иметь пустой `fields`;
иначе запись отклоняется с `InvalidReferenceError`. При известном активном прогоне
неуспешный анализ можно сохранить в журнал без добавления покрытия.

`record_observation()` сам не разбирает AST или ответ upstream. Он проверяет
прогон, разрешает пары `(type_name, field_name)` только внутри его снимка,
отвергает отсутствующие поля и атомарно сохраняет `ObservedRequest` и
`RequestFieldUsage`. Возвращается UUID наблюдения. Для неизвестного прогона
возникает `NotFoundError`, для завершённого — `ConflictError`; это Python-ошибки,
их отображение в HTTP-ответ прокси ещё не реализовано.

## 6. Какие поля считаются покрытыми

Текущий `get_graph()` учитывает привязку поля к наблюдению только при двух условиях:
`analysis_status == "success"` и `response_has_data is True`.

- `response_has_data=True` по [README](../README.md) означает наличие ключа `data`.
  Это включает `{"data":null}` и пустой объект `data`; это не проверка каждого
  значения ответа. Прокси ещё должен реализовать вычисление этого признака.
- `graphql_has_errors=True` не исключает запрос с `data` из покрытия.
  В текущем агрегаторе нет дополнительного фильтра по HTTP-статусу.
  Ошибка транспорта без GraphQL-ответа с `data` не должна получать этот признак.
- Поле идентифицируется парой «тип схемы + имя поля», например `User.id`.
  Alias не создаёт отдельное поле покрытия. Повторы поля внутри одного наблюдения
  дедуплицируются; повторные HTTP-запросы увеличивают `hits`, но не число уникально
  покрытых полей. Встроенной дедупликации повторной записи всего запроса нет.
- `covered` означает `hits > 0`. Покрытие отражает выбранные поля операции,
  а не доказательство выполнения каждого resolver или наличия ненулевого значения.
  Отсутствующие в операции поля ответа не считаются покрытыми автоматически.
- Требование к будущему Analyzer: учитывать выбранную `operationName`, fragments,
  aliases и применимые `@skip`/`@include` с variables. Поддержка этих конструкций,
  а также правила разрешения interface/union ещё не подтверждены реализацией.
  Нельзя автоматически считать покрытыми все реализации интерфейса.
- `__typename`, introspection-типы/поля и поля input-типов не импортируются как
  учитываемые выходные поля. Аргументы и значения variables не являются полями
  покрытия. Deprecated-поля остаются в схеме и учитываются.

Например, для схемы из `frontend-api.md` запрос `query { users { id name } }`
выбирает `Query.users`, `User.id`, `User.name`: 3 из 5 полей, 60%.
Повтор запроса оставляет 60%, увеличивая hits этих полей до 2.
Без реализации Analyzer и записи наблюдений один HTTP-проксирующий запрос
этот результат не создаст.

**Ограничение метрики в текущем main:** общая `summary` включает поля `OBJECT`
и `INTERFACE`. PR #6 изменяет её на поля только `OBJECT`; интерфейсы остаются
в графе. До слияния нельзя ожидать исправленный знаменатель на схемах с
интерфейсами. Числа для схемы примера выше от этого исправления не зависят.

## 7. REST API для карты покрытия и диагностики

| Запрос | Назначение |
| --- | --- |
| `GET /api/schemas/{schemaId}/graph` | Карта снимка до тестов: `runId=null`, `covered=false`, `hits=0` |
| `GET /api/runs/{runId}/coverage` | Карта и метрики конкретного прогона, во время выполнения и после завершения |
| `GET /api/runs/{runId}/requests?limit=100&offset=0` | Журнал запросов от новых к старым; `limit` от 1 до 500, `offset >= 0` |

Форма `CoverageGraph` одинакова для карты схемы и прогона:

| Путь в ответе | Как использовать во фронтенде |
| --- | --- |
| `schemaId`, `runId` | Привязка карты к снимку и прогону |
| `summary.totalFields`, `coveredFields`, `coveragePercent` | Общие счётчики и готовый процент сервера |
| `types[].name`, `kind` | Узлы; граф содержит OBJECT, INTERFACE, UNION |
| `types[].totalFields`, `coveredFields`, `coveragePercent` | Метрики узла; процент `null`, если у типа нет полей |
| `types[].fields[]` | `name`, `returnType`, `targetType`, `deprecated`, `covered`, `hits` |
| `relations[]` | `fromType`, `field`, `toType`, `covered`; ключ ребра — исходный тип + поле |

Поля `coveredFields` и `coveragePercent` в строке `summary` находятся внутри
`summary`, аналогичные поля типов — внутри каждого элемента `types`.
Связь покрыта, если покрыто соответствующее исходное поле. Для scalar-поля
`targetType=null`, отдельного ребра нет. Общий процент пустой схемы — `0.0`;
`null` у типа без полей не нужно отображать как 0%.

Фронтенд использует серверные проценты. Журнал помогает отличить отсутствие
трафика от `parse_error`, `validation_error`, `unsupported`, `internal_error`
и ответов без `data`. Запись содержит `operationName`, `operationType`,
`httpMethod`, `httpStatus`, `analysisStatus`, `responseHasData`, `graphqlHasErrors`,
`durationMs`, `errorCode`, UUID и время; тел запросов/ответов в REST-журнале нет.
Нулевое покрытие само по себе не доказывает, что приложение не использовало поля:
в текущем `main` сбор через HTTP отсутствует.

## 8. Минимальное подключение существующего Playwright-набора

Это выдержки для внешнего E2E-репозитория, не новый Playwright-проект или тест.
Предварительно нужны работающая сквозная интеграция из раздела 10, реальный SDL,
настоящий upstream и приложение, уже настроенное обращаться к прокси.

Минимальная fixture добавляет заголовок только запросам к точному URL прокси.
Существующие тесты должны импортировать её `test` вместо базового `test`;
при наличии своих fixtures нужно встроить этот шаг в их настройку context.
Маршрут устанавливается до навигации, другие GraphQL-маршруты с подменой ответов
для этого набора должны быть отключены.

```ts
import { test as base, expect } from '@playwright/test';

export const test = base.extend({
  context: async ({ context }, use) => {
    const runId = process.env.COVERAGE_RUN_ID;
    const proxyUrl = process.env.COVERAGE_GRAPHQL_URL;
    if (!runId || !proxyUrl) {
      throw new Error('COVERAGE_RUN_ID and COVERAGE_GRAPHQL_URL are required');
    }
    const endpoint = new URL(proxyUrl);
    await context.route(url => url.href === endpoint.href, async route => {
      const request = route.request();
      await route.continue({
        headers: {
          ...await request.allHeaders(),
          'x-coverage-run-id': runId,
        },
      });
    });
    await use(context);
  },
});

test.use({ serviceWorkers: 'block' });
export { expect };
```

`route.continue()` отправляет запрос в сеть. Здесь не меняются URL, метод, тело,
исходный `Authorization` и ответ; не используются `fulfill`, HAR или локальные
GraphQL-ответы. Cookie остаётся под управлением браузера. Точный matcher требует,
чтобы приложение использовало тот же URL, включая query string, что и
`COVERAGE_GRAPHQL_URL`. Redirect на этом endpoint для демо не нужен.
Service Workers блокируются, чтобы они не обходили перехват context.
Пример опирается на официальные API Playwright:
[context.route](https://playwright.dev/docs/api/class-browsercontext#browser-context-route),
[route.continue](https://playwright.dev/docs/api/class-route#route-continue)
и [переопределение fixtures](https://playwright.dev/docs/test-fixtures#overriding-fixtures).

Один внешний оркестратор создаёт общий прогон до запуска workers и завершает его
после выхода Playwright. Например, следующий Bash-фрагмент выполняется в уже
существующем E2E-репозитории с `curl`, `jq` и установленным Playwright:

```bash
set -euo pipefail
: "${COVERAGE_API_URL:?REST API base URL is required}"
: "${COVERAGE_SNAPSHOT_ID:?Imported snapshot UUID is required}"
: "${COVERAGE_GRAPHQL_URL:?Proxy GraphQL URL is required}"

payload=$(jq -n --arg snapshotId "$COVERAGE_SNAPSHOT_ID" \
  '{snapshotId: $snapshotId, name: "External E2E", metadata: {}}')
run=$(curl --fail-with-body --silent --show-error \
  -H 'Content-Type: application/json' --data "$payload" \
  "$COVERAGE_API_URL/api/runs")
COVERAGE_RUN_ID=$(jq -er '.id' <<< "$run")
export COVERAGE_RUN_ID COVERAGE_GRAPHQL_URL

finish_and_report() {
  test_status=$?
  trap - EXIT
  curl --fail-with-body --silent --show-error -X POST \
    "$COVERAGE_API_URL/api/runs/$COVERAGE_RUN_ID/finish" || exit 1
  curl --fail-with-body --silent --show-error \
    "$COVERAGE_API_URL/api/runs/$COVERAGE_RUN_ID/coverage" || exit 1
  exit "$test_status"
}
trap finish_and_report EXIT
npx playwright test
```

`COVERAGE_API_URL` — адрес API без завершающего `/`, например
`http://localhost:8000`; `COVERAGE_GRAPHQL_URL` — полный адрес `/graphql`.
Переменные `COVERAGE_*` — соглашение примера во внешнем наборе, а не новые
настройки бэкенда. Приложению нужен его собственный механизм настройки GraphQL URL.
Аутентификация приложения выполняется существующим способом тестового набора.

Тесты должны дождаться GraphQL-ответов, а teardown — остановить фоновые запросы
до выхода процесса. Оркестратор предполагает гарантию записи до ответа из
раздела 1. Отчёт выводится и при падении тестов, исходный ненулевой exit code
Playwright сохраняется, а ошибка завершения/получения отчёта тоже даёт ошибку.
EXIT trap не спасает от SIGKILL или потери runner: незавершённый run потребует
явного `/finish` оператором. Удалять или переиспользовать чужой running-прогон нельзя.

## 9. Необходимые компоненты демонстрационного приложения

| Компонент | Что необходимо для реального демо |
| --- | --- |
| GraphQL upstream | Работающий сервер с настоящими resolvers, данными и авторизацией; доступен из прокси |
| Тестируемое веб-приложение | Существующие пользовательские сценарии, которые действительно вызывают GraphQL; GraphQL URL настраивается на прокси |
| HTTP Proxy | `/graphql`, настроенный upstream, прозрачная пересылка, извлечение runId и запись наблюдений |
| GraphQL Analyzer | Разбор/валидация операции по снимку схемы и выдача `AnalysisResult` с `FieldReference` |
| PostgreSQL и Coverage REST API | Импорт реального SDL, создание/завершение run, сохранение и агрегация наблюдений |
| Внешний E2E-набор | Настоящие тесты, авторизация приложения, общий runId и управление жизненным циклом |
| Фронтенд карты | Выбор сервиса/снимка/прогона, узлы и связи из REST API, статусы покрытия и журнал |
| Подключение окружения | Доступность адресов, CORS/origin и корректная передача заголовков на всех промежуточных узлах |

До/после запуска можно сравнить карту схемы и карту прогона, проверить реальный
результат пользовательского действия и рост hits при повторном запросе.
Заранее заполненные наблюдения, ручные field IDs или подмена GraphQL-ответов
не доказывают работу этой интеграции.

## 10. Ограничения, незавершённые PR и расхождения

Состояние зависимостей на дату проверки:

| Работа | Статус и влияние |
| --- | --- |
| [PR #3: HTTP proxy](https://github.com/QualiMeter/GraphQL-Coverage-Proxy-Beckend/pull/3) | Открыт. Добавляет `POST /graphql`, `TARGET_GRAPHQL_URL`, передачу Authorization и удаление служебного заголовка. Не добавляет Analyzer, проверку runId или запись покрытия; одного слияния недостаточно |
| Analyzer и связь с `record_observation()` | В проверенном `main` и открытых PR реализации нет. Нужны анализ по снимку, атрибуция, признаки ответа и гарантия завершения записи |
| [PR #6: метрика OBJECT](https://github.com/QualiMeter/GraphQL-Coverage-Proxy-Beckend/pull/6) | Открыт. Исключает поля INTERFACE из общей summary; нужен для ожидаемой метрики только по OBJECT |
| [PR #2: отчёт аудита](https://github.com/QualiMeter/GraphQL-Coverage-Proxy-Beckend/pull/2) | Открыт, содержит отчёт и описание проблемы знаменателя; функциональность сбора не добавляет |

В `main` доступны только SDL-импорт и REST API; удалённая introspection ещё
не реализована. Контракты не содержат API Analyzer или публичного endpoint
для `record_observation()`. Поддержка batching, persisted queries, multipart,
GET GraphQL и streaming не гарантирована. PR #3 поддерживает только HTTP POST,
буферизует тела в памяти, не поддерживает WebSocket-подписки и streaming,
не следует redirects; таймаут каждой сетевой операции — 30 секунд.
В его реализации ошибки сети дают 502, таймауты — 504, отсутствующий/некорректный
upstream — 503. Эти коды относятся к PR #3, а не к текущему `main`.

REST API сейчас без авторизации; runId тоже не секрет доступа. Окружение должно
быть ограниченным тестовым. `/health` подтверждает ответ процесса, но не
готовность БД, upstream или сквозной записи покрытия. Сопоставления с конкретным
тест-кейсом, автоматического закрытия зависших прогонов и REST-статуса «тесты
упали» нет. Наличие полей в схеме ещё не подтверждает поддержку AST-конструкций
анализатором.

При сверке обнаружено следующее расхождение существующего описания с кодом:
таблица ошибок `frontend-api.md` обобщённо описывает 404 как отсутствие ресурса,
но `GET /api/schemas?serviceId={uuid}` и `GET /api/runs?snapshotId={uuid}`
не проверяют существование родительского ресурса и для неизвестного корректного
UUID возвращают 200 и пустой массив. Для чтения карты/завершения неизвестного
прогона 404 действительно реализован. Исходный документ и код здесь не исправляются.

Важные уточнения при чтении документации: фраза «для первого демо достаточно
шагов 1–8» в `frontend-api.md` описывает REST-сценарий, но в текущем `main`
не означает готовность E2E-сбора. Обещания готового `/graphql` в README и
frontend-контракте нет: оба явно отмечают его отсутствие. Исправление summary
из PR #6 также нельзя считать уже действующим контрактом текущего `main`.
