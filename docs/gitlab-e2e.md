# Запуск E2E через GitLab из Coverage Proxy

Бэкенд самостоятельно обращается к GitLab API v4 и хранит связь с прогоном.
Доступность QA/TestLab и открытая вкладка браузера не требуются.

## API для фронтенда

Все пути ниже относительны к базовому URL API, включая префикс reverse proxy,
если он настроен. Браузер использует существующую Coverage-сессию; для POST
нужны `Origin` своего сайта и `X-CSRF-Token` из `/api/auth/session`.
GitLab host, project ID, токены и произвольные CI-переменные клиент не передаёт.

1. Выбрать сервис через `GET /api/services` и снимок через
   `GET /api/schemas?serviceId=<UUID>`.
2. Получить ветки: `GET /api/services/<serviceId>/gitlab/branches?page=1`.
   Ответ — массив имён, максимум 100 за страницу. Запрашивать следующие страницы
   до неполной/пустой страницы. Нужны роль operator/admin и доступ к сервису.
3. Создать прогон: `POST /api/runs/gitlab`:

```json
{
  "serviceId": "11111111-1111-4111-8111-111111111111",
  "snapshotId": "22222222-2222-4222-8222-222222222222",
  "ref": "main",
  "name": "E2E regression"
}
```

UUID в примере иллюстративны: использовать реальные записи из API.
`name` необязателен. `ref` должен быть существующей веткой. Ответ — `202 Accepted`:

```json
{
  "runId": "33333333-3333-4333-8333-333333333333",
  "pipelineId": 42,
  "pipelineUrl": "https://gitlab.com/group/project/-/pipelines/42",
  "pipelineStatus": "pending",
  "runStatus": "running",
  "errorCode": null,
  "createdAt": "2026-11-17T10:00:00Z",
  "finishedAt": null,
  "trackingFinished": false
}
```

4. Читать сохранённый статус через `GET /api/runs/<runId>/gitlab`.
   Формат такой же. Нужна аутентификация, минимум viewer и явный доступ к сервису
   либо admin. Публичность сервиса сама по себе не открывает GitLab-метаданные.
   GET не обращается в GitLab и не управляет завершением прогона.
5. Во время и после выполнения обновлять существующую карту:
   `GET /api/runs/<runId>/coverage`; история — `GET /api/runs?snapshotId=<UUID>`.
   Дополнительно доступны `/stats`, `/operations`, `/requests` по прежним правилам.

При таймауте POST к GitLab ответ остаётся `202`, но `pipelineId` и `pipelineUrl`
могут быть null, `pipelineStatus=launch_unknown`, `errorCode=gitlab_network_error`.
Нельзя автоматически повторять создание: опрашивать выданный runId.
Если клиент потерял ответ или получил 503 при сохранении результата, сначала
проверить историю снимка. Активный/невыясненный запуск защищён от дублей в БД.

Ошибки: 401 — нет аутентификации, 403 — роль/CSRF/Origin, 404 — нет доступа или
снимок не принадлежит сервису, 409 — активный прогон либо незавершённая сверка,
422 — неверный JSON, 502 — ошибка GitLab, 503 — конфигурация/хранилище недоступны.
Однозначный отказ после создания прогона возвращает 502 с
`detail: {"code":"gitlab_rejected", "runId":"<UUID>"}`; код также сохраняется.
Другие безопасные коды: `gitlab_unauthorized`, `gitlab_forbidden`,
`gitlab_not_found`, `gitlab_unavailable`, `gitlab_invalid_response`,
`gitlab_destination_unavailable`. Тела ошибок GitLab и исключений не выдаются.

## Серверная конфигурация

| Переменная | Назначение |
| --- | --- |
| `GITLAB_ENABLED` | `false` по умолчанию; `true` включает API запуска и монитор в lifespan |
| `GITLAB_HOST` | Доверенный HTTPS origin, по умолчанию `https://gitlab.com`; без пути, query, credentials |
| `GITLAB_TOKEN` | Серверный project/personal access token с `api` scope и ролью, позволяющей запуск выбранных веток и чтение пайплайнов/variables |
| `GITLAB_SERVICE_PROJECTS` | JSON-привязка `{"<существующий service UUID>":12345}`; числовые project IDs |
| `GITLAB_COVERAGE_URL` | Доступный runner базовый URL Coverage, для текущего стенда `https://graphql.rebyte.fun`; QA добавляет `/graphql`; без ключей и query |
| `COVERAGE_MIN_PERCENT` | Порог 0–100, по умолчанию 80 |
| `GITLAB_POLL_SECONDS` | Интервал 2–300 секунд, по умолчанию 10; ошибки увеличивают паузу до 300 секунд |
| `GITLAB_MAX_RUN_SECONDS` | Предельное время сбора 60–86400 секунд, по умолчанию 3600 |

Для текущего развёртывания задавать:

```dotenv
GITLAB_COVERAGE_URL=https://graphql.rebyte.fun
```

Бэкенд передаёт это значение в `COVERAGE_URL` без завершающего `/`, а QA
формирует `${COVERAGE_URL}/graphql`: здесь это `https://graphql.rebyte.fun/graphql`.
Путь `/coverage/` на этом стенде принадлежит frontend, а не API-прокси.
В другом развёртывании допустим реальный префикс reverse proxy: например,
`https://coverage.example/team/proxy` → `https://coverage.example/team/proxy/graphql`.
Префикс должен маршрутизировать также `/api/...`; глобального запрета путей нет.

Настройки читаются через конфигурацию приложения. При включённой интеграции
некорректная конфигурация не позволяет стартовать процесс без монитора.
В Compose необходимые переменные проброшены в API. Токен не хранится в таблице,
не возвращается в API и передаётся GitLab только заголовком `PRIVATE-TOKEN`.
Не используются trigger tokens, CI_JOB_TOKEN или определение типа по префиксу.
Для этой операции требуется API-токен, умеющий также читать pipeline variables.
Официальные контракты: [Pipelines API](https://docs.gitlab.com/api/pipelines/),
[Branches API](https://docs.gitlab.com/api/branches/).

Исходящие соединения используют существующую DNS/IP-проверку и PinnedTransport:
без redirects, proxy-env и автоматических retries. Даже записанный в БД host
не выбирает адрес соединения: он должен совпадать с текущей серверной настройкой.
Публичные HTTPS GitLab работают по умолчанию; частные GitLab требуют отдельного
согласованного расширения политики исходящих соединений. Не ослаблять защиту
SSRF ради запуска в production.

## Подготовка GitLab и QA

- В серверной привязке указать проект с настоящими E2E и нужными ветками.
- Токену дать минимально необходимую роль и `api` scope, доступ к защищённым
  веткам при необходимости. Права на override pipeline variables также должны
  разрешать этому пользователю передавать переменные запуска.
  Coverage operator с grant на сервис выбирает ветки привязанного проекта;
  в GitLab запросы выполняются от серверного токена, а не от GitLab-аккаунта
  оператора. Поэтому права токена и защита веток проекта задают предел доступа.
- В `.gitlab-ci.yml` разрешить `CI_PIPELINE_SOURCE == "api"` на уровне workflow
  и jobs. Бэкенд использует `POST /projects/:id/pipeline`, а не trigger endpoint.
- Читать строго `COVERAGE_RUN_ID`, `COVERAGE_URL`, `COVERAGE_MIN_PERCENT`.
  Run ID — настоящий UUID; fallback на `latest` и CI_PIPELINE_IID запрещён.
- E2E не создают свой прогон и не вызывают `/finish`. Они направляют запросы на
  `${COVERAGE_URL}/graphql`, передавая `X-Coverage-Run-Id: ${COVERAGE_RUN_ID}`.
  Все запросы должны завершиться и сохраниться до завершения тестового job.
- Runner должен иметь собственную заранее настроенную аутентификацию Coverage.
  Бэкенд **не передаёт серверный COVERAGE_API_KEY в пайплайн**. Безопасный вариант
  для демо — отдельный пользователь operator с доступом только к демо-сервису:
  CI получает его пароль из masked/protected GitLab variables, входит через
  `/api/auth/login` с правильным Origin, сохраняет cookie и передаёт Origin/CSRF
  на POST `/graphql`. Учесть доступность protected variables на выбранной ветке.
  Учётные данные CI должны управляться администраторами проекта, а не фронтендом.
- Quality gate может читать карту уже во время `running`; не ждать `completed`
  внутри пайплайна: прогон завершается после окончания самого пайплайна.

| Переменные и UUID | `external-run-gate` читает ровно `COVERAGE_RUN_ID`, `COVERAGE_URL`, `COVERAGE_MIN_PERCENT`. Реализовать и проверить собственную сессию QA для GraphQL и чтения карты с grant на нужный сервис. Публичное чтение карты не заменяет авторизацию записи. Передача серверного ключа в pipeline недопустима. |
| GitHub bridge | [`github-bridge.yml`](https://github.com/QualiMeter/GraphQL-Coverage-Proxy-QA/blob/08f5568e222765400fd3aa1d6117b0aaeef60b15/examples/gitlab/github-bridge.yml) требует protected ref и полный `QA_GITHUB_SHA`; backend передаёт только три Coverage-переменные. Полный режим backend-managed E2E с отдельной сессией QA в проверенных исходниках
ещё не опубликован. До его публикации и совместной проверки это зависимости
включения интеграции, а не подтверждение сквозной совместимости. Настройки живого
GitLab-проекта и его CI variables здесь не проверялись. QA-репозиторий в этом PR
не меняется; реальные пайплайны не запускались.

## Жизненный цикл и восстановление

Миграция `20261121_gitlab_pipelines` создаёт отдельную таблицу с run_id, host,
project/ref, pipeline ID/URL/status, сроком сбора, временем завершения, безопасным
кодом ошибки, номером страницы сверки и арендой фоновой проверки. Старые прогоны
не изменяются. `TestRun` сохраняет только running/completed/failed.

| Событие GitLab | Результат TestRun |
| --- | --- |
| pending/running/created/preparing/manual/scheduled/waiting_for_resource, новые неизвестные статусы | running до результата или предельного срока |
| success/failed/canceled/skipped | completed, все накопленные наблюдения сохраняются |
| Однозначный отказ запуска или ошибка проверки ветки до POST | failed, блокировка снимка освобождается |
| Неоднозначный POST: timeout/network/5xx/429/невалидный успешный ответ | running + сверка по UUID, повторного POST нет |

Создание run и intent атомарно, под существующей блокировкой сервиса и уникальным
ограничением одного running на snapshot. Между commit и POST есть неизбежное окно
сбоя процесса: даже если POST не был выполнен, монитор только ищет пайплайн, не
запускает его заново. Получение списка с `source=api`, ref и created_after,
постраничное чтение variables и точное совпадение COVERAGE_RUN_ID восстанавливают
связь. Страница сверки сохраняется; за один проход проверяется не более двух
записей, чтобы три HTTP-запроса укладывались в общий таймаут даже при медленном GitLab.

Каждый процесс приложения запускает asyncio-monitor из lifespan. Проверка
получает строку через `FOR UPDATE SKIP LOCKED`, аренду 90 секунд и уникальный
lease token; освобождает транзакцию, делает HTTP и атомарно сохраняет результат.
Старый worker не может перезаписать результат новой аренды. Внешние запросы
ограничены таймаутами 15 секунд; полный проход сверки — 60 секунд. Фоновая задача
отменяется при shutdown, аренды истекают и подхватываются после restart.
Ручное завершение GitLab-прогона через прежний `/finish` возвращает 409.

При предельном сроке известный пайплайн закрывает сбор как completed,
неизвестный запуск — как failed. Покрытие не удаляется. `errorCode` становится
`tracking_deadline_exceeded`. Пайплайн продолжает сверяться, его реальный статус
не подменяется таймаутом. На снимке сохраняется карантин: и ручной, и новый GitLab
запуск дают 409 до выяснения результата. Это сознательный выбор: нельзя безопасно
освободить снимок и разрешить повторный запуск, если неизвестно, идёт ли первый.
После выяснения терминального статуса блокировка снимается автоматически.
Исторический failed после неизвестного запуска не переписывается задним числом.

Если оператор независимо убедился в GitLab, что пайплайн с этим UUID не создан,
после истечения срока сбора и вне активной аренды можно локально выполнить:

```bash
python -m app.gitlab_cli resolve-absent <run-UUID> --confirm-no-pipeline
```

Команда доступна только на сервере, не через HTTP. Она допускает только failed
неизвестный запуск без pipeline ID, фиксирует `operator_confirmed_not_created`
и освобождает карантин. Не использовать её при неизвестном результате проверки.
Известный активный пайплайн сначала закончить/отменить средствами GitLab.
Не выключать GITLAB_ENABLED и не менять host до завершения всех управляемых
пайплайнов. При длительном отказе самой БД завершение возможно после её восстановления.

## Проверка и включение на VPS после ревью

1. Применить миграции `alembic upgrade head`; сделать резервную копию штатным
   процессом эксплуатации. Для отката приложения сначала дождаться завершения
   управляемых пайплайнов: предыдущая версия не знает о GitLab-защите `/finish`.
2. Настроить переменные из таблицы на сервере; при изменении env перезапустить API.
   Секреты не помещать в Git и не выводить `docker compose config` с их значениями.
3. Выполнить локальные тесты с отдельными DATABASE_URL и TEST_DATABASE_URL:
   `python -m pytest -q`, `python -m pip check`, `alembic check`.
   GitLab HTTP имитируется, реальные пайплайны автоматические тесты не запускают.
4. После обновления QA вручную проверить роли/CSRF, список веток, один запуск,
   рост покрытия, 409 при повторе и ручном finish. Закрыть вкладку, перезапустить
   API, проверить автоматическое завершение. Повторить failed/canceled сценарии.
5. Для Swagger открыть `/docs`, выбрать POST `/graphql`, Authorize существующим
   способом и передать UUID running-прогона. Try it out показывает JSON
   `{"query":"{ __typename }"}` и отправляет его с application/json.

В этом изменении нет деплоя, merge, изменения QA или реального запуска GitLab.
